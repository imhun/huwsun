## 问题

```rust
pub struct MessageProcessor {
    messages: Vec<String>,
    statistics: Statistics,
}

impl MessageProcessor {
    pub fn process_pushed_messages(&mut self) {
        for message in self.messages.drain(..) {
            self.process_message(message); // 错误：self 已被借用
        }
    }
}
```

`drain(..)` 可变借用了 `self.messages`；`self.process_message` 在编译器看来可能改动**任意字段**，包括 `messages`，于是冲突。这个判断逻辑上没错，但这段代码本身完全合理。

老手会绕：把 `messages` 换成空 vec、改用 `pop()`、或者把 `process_message` 改成 `Statistics` 的方法。都不理想。

根因是：**借用检查器不知道 `process_message` 只访问 `statistics`。**

## 方案：给结构体类型加一个字段清单

```text
RustType := StructName<...>
         |  StructName<...> { .. }         // 所有字段都能访问
         |  StructName<...> { (fields),* } // 只列出的字段能访问
```

`MessageProcessor { statistics }` 读作“一个 `MessageProcessor`，但只有 `statistics` 字段能被访问”；`{ .. }` 等价于今天的写法。

view type **遵守可见性规则**：只有能直接写出该字段的上下文，才允许写它。最方便的用法是放在 `self` 上：

```rust
impl MessageProcessor {
    fn process_message(&mut self {statistics}, message: String) {
        //  等价于 self: &mut MessageProcessor {statistics}
    }
}
```

只改这一处，`process_pushed_messages` 就通过了——两条 loan 落在不同位置，不再重叠。

## 借用检查器怎么支持

碰到借用表达式时记一条 loan，记录借用的**位置**、**方式**（可变 / 共享）和**生命周期**。用了 view 的借用就记多条：

| 借用写法 | 记几条 loan |
|---|---|
| `&mut self` | 一条，对 `self` |
| `&mut self {field1, field2}` | 两条，分别对 `self.field1` 和 `self.field2` |

例子里用户从没手写过 `&mut`，是方法调用时**自动加的**，而 auto-ref 会自动引入 view 借用：

```rust
// self.process_message(message) 展开成
MessageProcessor::process_message(&mut *self { statistics }, message)
```

## 这是纯静态的

view type 不改变编译结果，只是给借用检查器更多信息——`process_message` 仍然只收一个指向 `self` 的指针。

对比今天的绕法：把方法改成收 `&mut Statistics` 的关联函数，不但调用处要写 `Self::process_message(&mut self.statistics, ..)`，而且**改变了编译结果**——传的不再是 `MessageProcessor` 的引用。一个字段时无所谓，需要多个字段时逐个传就不划算了。

## 常见问题

**实现难吗。** 不难，只要有人接手，作者认为今年就能落地。

**隐私怎么算。** view type 里的字段必须对当前代码可见，包括 auto-ref 插入的那些：

```rust
impl MessageProcessor {
    pub fn process_message(&mut self {messages}, message: String) { ... }
    // 模块内合法，但会 lint
}
// 模块外调用会展开成 &mut mp {messages}，引用私有字段 = 错误
```

在模块内引用私有字段本身合法，但会触发 lint，道理和“pub 方法接受私有类型的参数”一样——虽然合法，但这个方法在模块外根本没法调用。

**那 public 方法岂不是用不了。** 基本是，除非 view type 引用的都是 public 字段。

**只能用于私有方法，会不会太受限。** 会，但作为起点够了。作者的经验是这个问题**最常出现在私有 helper 上**；公共场景也会遇到，但少得多，而且那类情况往往本来就该重构类型、把分组暴露给用户。留给后来的 [abstract fields](https://smallcultfollowing.com/babysteps/blog/2025/02/25/view-types-redux/) 解决。

**老是要写同一组字段，太啰嗦。** 确实。将来希望能有“幽灵字段”或“抽象字段”，同样是 MVP 之后的事。

**字段集能不能推断。** 可以研究，row polymorphism 最对口。作者**大概率会把它做成默认行为**——即 `&mut place` 总是引入 view type，只是实践中通常推断成“所有字段”。但这对 Rust 的推断系统是个不小的扩展，所以 MVP 先用 auto-ref 覆盖绝大多数场景，剩下用显式语法。

那为什么不一开始就靠推断？代价是三条：

| 代价 | 说明 |
|---|---|
| 方法之间产生依赖 | 推断变难，极端情况下甚至不可判定 |
| 非局部错误 | 改一个方法的方法体会让另一个方法报错（想想 `futures` 和 `Send` 带来的困惑） |
| 编译器更复杂 | 并行化变难 |

结论是**分阶段**：无论如何都需要一种能精确说明“哪些字段在哪里被访问”的方式，所以先加显式的，推断以后再补。

**为什么不脱糖成“传字段引用”。** 两个原因：更复杂——改借用检查器是相对直接的改动，而那种脱糖会散落到编译器各处，诊断信息也复杂得多；以及它**要求改变运行时行为**，这个例子里根本没必要。

**语法歧义怎么办。** 作者本想让 `Struct { field1, field2 }` 呼应结构体构造语法，但借用表达式里就有歧义：

```rust
let foo = &mut some_variable { field1 };
// 这是变量还是字段名？
```

三个方向：

- **让它工作。** 并非真有歧义，只是需要语义消歧（有些情况得等名字解析完成）。Rust 里有先例——`None` 到底是变量绑定还是枚举变体。
- **只给借用换新语法**，比如 `&mut {field1} in some_variable`。反正显式借用形式很少手写。
- **整体换一套语法**，比如引入关键字。这块作者想听更多建议。
