> 来源：[Panics vs cancellation, part 1](https://smallcultfollowing.com/babysteps/blog/2022/01/27/panics-vs-cancellation-part-1/)，Niko Matsakis，2022-01-27

Rust 里取消一个 future 就是 drop 它。这一句话解释了取消的大部分性质：future 挂起时拥有的是栈帧上的局部变量，drop 会把它们清掉，等价于在 `await` 那个位置把栈展开。

<!-- more -->

于是取消和 panic 在机制上是同一件事，差别只有两处：

| | 触发方 | 能否拦截 |
|---|---|---|
| panic | 线程自己执行到的代码 | 可以 `catch_unwind` |
| 取消 | 外部，future 的结果不再被需要时 | 不能，展开挡不下来 |

第二条是有代价的。Java 弃用 `Thread.stop` 就是因为这个：外部中断一个正在运行的线程，程序没法知道它停在哪、留下什么中间状态。

## 两者都只适合粗粒度恢复

根本原因是**不变量**——让不变量在每个操作的开头和结尾成立很容易，让它**始终**成立非常难，因为很多代码需要先把数据弄成不一致、再修好。

```rust
fn copy_data(from_file: &File, to_socket: &Socket) {
    let buffer = from_file.read();
    let parsed_items = parse(buffer);
    parsed_items.send(to_socket);
}
```

这段代码没有任何显式修改，看起来随时打断重跑都没事。但 `from_file` 的游标是隐式状态：`parse` 或 `send` 中途失败，刚读到（也许已解析）的数据就丢了，下次调用从断点继续，不会重读。

这就是要用 `?` 的原因——让错误显形：

```rust
fn copy_data(from_file: &File, to_socket: &Socket) -> eyre::Result<()> {
    let buffer = from_file.read()?;
    let parsed_items = parse(buffer);
    parsed_items.send(to_socket)?;
}
```

而且 `?` 不强制往上抛，可以就地恢复（`send` 失败时会把消息还回来）：

```rust
match parsed_items.send(to_socket) {
    Ok(()) => (),
    Err(SendError(parsed_items)) => recover_from_error(parsed_items),
}
```

同一段代码改成 async，可中断的位置就从“任意处”收缩成 `await` 点：

```rust
async fn copy_data(from_file: &File, to_socket: &Socket) {
    let buffer = from_file.read().await;
    let parsed_items = parse(buffer);
    parsed_items.send(to_socket).await;
}
```

停在最后一个 `await` 时，future 里存着 `buffer` 和 `parsed_items`，drop 就是把这两样析构掉。取消在 Rust 里没有别的机制。

## Rust 把 panic 恢复限制在线程边界

`catch_unwind` 当年加入时争议很大：异常擅长把错误往上传，不擅长从错误里恢复，一旦提供了恢复手段，人们就会以为哪儿都能恢复。真正可行的只有**非常粗的粒度**，比如接住异常重启主循环——Erlang 那句 “let it crash” 说的就是这个，也是这个思路最干净的版本。

所以 Rust 的规定是：恢复只发生在线程边界。线程拥有自己的全部状态，panic 就连状态一起丢掉。

这个边界并不严实：线程之间可以直接共享 `Mutex`，也可以像 `copy_data` 那样通过文件、channel 间接共享。锁中毒是拿来兜这些情况的。作者认为这个概念本身没问题，问题出在实现的易用性上。

他还提到一个没想清楚的问题：panic 至今仍是 Rust 可靠性故事里比较弱的一环——即使只是目前这种受限形态，也有不少人反馈不好用。
