两个讨论了多年的人体工学特性，都卡在实现上很久，现在有办法做了。但它们带着同一个副作用：**semver 隐患**——看起来无害的改动实际会破坏使用者。

<!-- more -->

## semver 隐患是什么

Rust 里已经有这类东西，最典型的是 `Send`。`Send` 是 auto trait，只要所有字段都是 `Send`，类型就自动是 `Send`。方便，但推论是：给 struct 加一个类型不线程安全的私有字段（比如 `Rc<T>`）**可能是破坏性改动**——本来就有人把 `MyStruct` 送到别的线程去跑。

规律是：凡是试图自动推导 crate 公开接口某一部分的机制，都会带来 semver 隐患。

## perfect derive

在泛型类型上派生 `Clone` 时，derive 一律要求**所有**泛型参数都 `Clone`，而这往往不必要。

```rust
#[derive(Clone)]
struct List<T> {
    data: Rc<T>,
    next: Option<Rc<List<T>>>,
}
```

现在会生成 `impl<T: Clone> Clone for List<T>`。但 `T` 只出现在 `Rc` 里，clone 只是把引用计数加一，根本不碰 `T`。perfect derive 改成**每个字段一条 where 子句**，算出恰好需要的约束：

```rust
impl<T> Clone for List<T>
where
    Rc<T>: Clone,
    Option<Rc<List<T>>>: Clone,
{ ... }
```

实现上的障碍是要让 trait 匹配允许循环（现在只有 auto trait 允许），稍有疏忽就会让 Rust 变得很不 sound。作者说这个问题已经解决。

代价是新的 semver 隐患：把 `List<T>` 重构成直接存 `T`（只改了私有字段的类型），`List<T>: Clone` 就只在 `T: Clone` 时成立了——下游可能编不过。

## 扩展 implied bounds

implied bound 是不用显式写的 where 子句。Rust 已经有两种：展开 supertrait（`T: Ord` 蕴含 `T: PartialOrd`）和 outlives 关系（`&'a T` 蕴含 `T: 'a`）。最大版本会扩展到**任意 where 子句**，于是这样写就够了，不用再重复约束：

```rust
struct RedBlackTree<T: Ord> { … }
fn insert_smaller<T>(tree: &mut RedBlackTree<T>, a: T, b: T) { ... }
```

隐患和 perfect derive 同源：删掉 struct 上的 `T: Ord`（比如为了加一些不需要排序的方法），就不再蕴含 `X: Ord`，依赖你库的 crate 可能编不过。而删约束本身是很常见的操作。

顺带一个容易搞错的点：从 struct 上删约束是 semver 兼容的，但从 **impl** 上删不行——`impl<T: Copy> MyTrait for Vec<T>` 改成 `impl<T> MyTrait for Vec<T>` 相当于引入新的 blanket impl（见 [RFC 2451](https://rust-lang.github.io/rfcs/2451-re-rebalancing-coherence.html)）。

## 几个方向

| 方案 | 代价 / 效果 |
|---|---|
| 直接接受隐患 | 不清楚实践中会不会真成问题，Rust 已经有一批类似隐患 |
| **crate 局部**的 implied bounds | 同 crate 内的 impl 能享受，下游还得重复写约束 |
| 给约束加**可见性**：`struct RedBlackTree<T: pub Ord>` | 默认私有（只在模块内隐含），声明成 `pub` 就等于纳入 semver 承诺 |
| 显式的 perfect derive，比如 `#[perfect_derive(…)]` | 让 perfect 变成显式选择加入 |

作者对“给每个参数显式写约束”那类老提案一向支持，但现在能实现 perfect derive 了，反而没那么确定——也许只要“总是加约束”（默认）和“用 perfect derive”两个选项就够。

核心诉求可以总结成一句：**一个接口里你承诺了哪些部分，应该清清楚楚。**

另外他希望能有顺手的工具帮库作者判断某个改动是否破坏 semver。这需要对两个版本做推理，所以有点难；已知有 [rust-semverer](https://github.com/rust-lang/rust-semverver)，但维护状况不明。理想是有一个能部署的 GitHub Action，在 review PR 时给提醒。
