## 背景：Sized 与 ?Sized

每个类型参数（`Self` 除外）默认带 `Sized`：

```rust
fn identity<T>(t: T) -> T { t }
```

它其实是这个的简写：

```rust
fn identity<T>(t: T) -> T where T: Sized { t }
```

`Sized` 意思是编译期能算出值的大小。绝大多数类型满足，例外不多。`[u32]` 不满足——单个 `u32` 是 4 字节，但不知道有多少个，所以算不出大小，栈上也放不下。

只按引用取值时不需要知道大小，可以显式退出默认：

```rust
fn by_ref<U>(t: &U) where U: ?Sized {}
```

## 为什么要做成层级

`Sized` / 非 `Sized` 两档盖不住所有需求：

| 情况 | 问题 |
|---|---|
| `extern` 类型 | 运行期也不知道大小 |
| Arm 的可伸缩向量扩展（SVE） | 同一个类型的每个值大小**相同**（不像 `[T]` 每个值长度可以不同），但具体多大要运行期才知道 |

所以要做成一个层级：

```text
MaybeSized        ← 所有值都实现，但不提供任何大小信息
  ↑ extends
MetadataSized     ← 值可以有不同大小，但拿到引用的 metadata 就能算出
  ↑ extends
Sized（默认）      ← 所有值大小相同，而且看类型就能算出
```

（`[T]` 和 `dyn Trait` 属于 `MetadataSized`。Arm 的 SVE 怎么塞进来是正交问题，这里不提；名字也还没定，`MetadataSized` 是 libs-api 团队偏好的叫法，不是作者自己最喜欢的。）

## 问题：`?Sized` 扩不到多层

`?Sized` 当初的假设是“用户要指明自己退出的是哪个默认 bound”——`?` 的意思是“我不确定它是不是 `Sized`”。这套说法放到多层结构里就不灵：

- 写 `?Sized` 到底指 `MetadataSized` 那一层，还是别的？
- 以后想在中间插一层怎么办——改 `?Sized` 的含义，还是让它一次掉两级？
- 中间那层还不稳定时更麻烦：总不能让 `?Sized` 指向一个不稳定 trait，万一最后决定不要它呢

## 方案：`only` bound

```rust
// 只是拿引用，不关心大小
fn by_ref<U>(u: &U) where U: only MaybeSized {}

// 需要知道值的大小
fn checks_size<V>(v: &V) where V: only MetadataSized {
    std::mem::size_of_val(v)
}
```

一个 `only` bound 同时表达两件事：

1. 和普通 bound 一样给出**最低要求**——`T: only MetadataSized` 意味着 `T` 至少实现 `MetadataSized`
2. 额外**关掉某些默认 bound**——不再自动加上 `T: Sized`

名字的来源：`T: Sized` 蕴含 `T: MetadataSized`，所以默认已经免费给了你一整条链；写 *only* MetadataSized 是说“我不需要整条链，到 `MetadataSized` 就够”。

两个附带好处：

- **语义是正面的。** `?` 说“我不需要这个”，`only` 说“我需要什么”，代码更好读
- **以后插新层不影响已有代码。** 假设想加 `Aligned`（大小算不出但**对齐**算得出），在中间插一层就行：`only MaybeSized` 和 `only MetadataSized` 的函数要求完全不变，新代码直接写 `only Aligned`。而且不卡稳定化——`T: only Aligned` 先按不稳定处理即可

`only` 也能组合。`T: only MetadataSized + Sized` 等价于 `T: Sized`，等于白写（同理 `T: only MetadataSized + Clone` 因为 `trait Clone: Sized` 也白写），这些情况计划加 warn-by-default 的 lint。

## 推广：其他“默认 bound 家族”

`only` 真正有潜力的一点是能引入**整族**新的默认 bound。作者举的例子是 [Move bound](https://smallcultfollowing.com/babysteps/blog/2025/10/21/move-destruct-leak/)（属于另一个特性，不在[当前 RFC](https://github.com/rust-lang/rfcs/pull/3729) 范围内）。

今天所有 Rust 类型都是“可移动”且“可遗忘”的：只要不再用原位置，就能把值 memcpy 到别处；也可以直接回收它占的内存而不跑析构。唯一的例外是 pin 之后不能再移动、而且内存复用前必须跑析构。**这条规矩挺烦人的**——无法保证析构一定运行，卡住了不少 unsafe 模式。[rayon 那样的 scoped tasks 靠析构保安全](https://smallcultfollowing.com/babysteps/blog/2016/10/02/observational-equivalence-and-unsafe-code/)：同步代码里成立，因为“栈帧回退却不跑析构”被定为 UB，所以栈上的局部变量一定会析构；但 async 里这招不管用。而且有时候**不跑析构**反而是想要的。

```text
Access
  ↑      ↑      ↑       ↑
Move（默认） Copy  Destruct  Leak
                          ↑
                      Forget（默认）
```

| trait | 含义 |
|---|---|
| `Forget`（默认） | 可以不跑析构就复用这块内存 |
| `Leak` | 可以不跑析构，但前提是那块内存永远不复用 |
| `Destruct` | 有值时可以通过跑析构来复用内存 |
| `Copy`（已存在） | 可以 memcpy 出去、原位置继续用；它不算默认，但相关所以列上 |
| `Move`（默认） | 只要不再用原位置，就能 memcpy 到新位置 |
| `Access` | 这一族的根，基本上就是所有值 |

编译器要新增两类检查：移动时检查类型是否实现 `Move`（今天总是允许）；离开作用域时检查局部变量要么已被移走，要么类型实现 `Destruct`。

几条推论：`T: only Destruct` 的值必须在返回前析构，不能移动（不知道它是否 `Move`），也不能泄漏或遗忘；`T: only Move` 的值只能移走，不能 drop；`T: only Access` 的值既不能移也不能丢，所以返回不了，但可以放在 `static` 里。

## 多家族共存时 `only` 怎么算

规则是：每个默认 trait 归属一个或多个家族；写 `only` bound 时，退出**该 trait 所属家族里的所有默认 trait**。

| 写法 | 退出 | 不动 |
|---|---|---|
| `T: only Move` | `Forget`、`Leak`、`Destruct` | `Sized` |
| `T: only Destruct` | `Forget`、`Leak`、`Move` | `Sized` |
| `T: only MetadataSized` | `Sized` | `Forget`、`Move` |

也可以再选回来：`T: only Move + Destruct` 表示能移动、能析构，但不能泄漏遗忘。

为什么不按“一次退出所有默认”来做（比如 `?default`）？两条理由：`T: only Move` 正说明“只退一个家族、保留 `Sized`”是常见需求，将来会有很多函数想退掉 `Sized` **或者** `Forget`，而不是两个都退；而且按家族退以后加新家族更容易。`Rc` 确实同时退两族，但那个组合不足以支持 `?default`——真正该支持的是 **trait alias**。

## 三个例子

```rust
// 只需要 Move：解构 self 把值移出来，再移进 Some
impl<T: only Move> Option<T> {
    fn map<U: only Move>(self, op: impl FnOnce(T) -> U) -> Option<U> { ... }
}

// 需要 Move + Destruct：alternate 可能用不上，得能丢
impl<T: only Move> Option<T> {
    fn or(self, alternate: Option<T>) -> Option<T>
    where
        T: Destruct,
    { ... }
}

// Rc：能装大小算不出来的东西；而且可能成环，永远无法保证析构
struct Rc<T: only MaybeSized + only Leak> {}
```

有意思的是 `Rc<T>` 自己可以实现 `Forget`，即使它装的内容不满足。

## 几个常见问题

**为什么不叫 `Drop` 而叫 `Destruct`。** 一是**不实现 `Drop` 也可以有析构**：`Drop` 指的是用户提供的析构逻辑，而编译器自己还会加一段逻辑（有时叫 drop glue）去析构所有字段。二是 `Drop` 这个 trait 本身也需要修订，换个名字才好容纳别的定制方式（pinned self、按值析构等）。

**能不能让 `Destruct` 蕴含 `Move`。** 早期提案里是这么设计的，那样 `Option::or` 就能只写 `U: only Destruct`。但 Alice Ryhl 等人指出存在**不可移动却必须析构**的类型，所以两者不该合并。

**trait alias 怎么帮忙。**

```rust
trait RefCountable = only Leak + only MetadataSized;
impl<T: only RefCountable> Rc<T> {}
```

注意：**没有 `only` 的话**，`T: RefCountable` 只是普通 bound，不会退出任何默认。定义 `trait Value = only Access + only MaybeSized;` 可以一次退出两个家族（因为 `Access` 和 `MaybeSized` 对所有类型都实现），但以后加新家族时 `Value` 会过时——所以这事可以晚点定：先加 Sized 族、再加 Access 族，观察实践中是不是经常两族一起退。作者判断不太会，因为 `T: only Move` 显然会很常见，而 `T: only Value + Move + Sized` 太笨重。

**和 const trait 的配合。** Arm 为 SVE 提的方案就是引入 `T: const Sized`（大小能在编译期算出来），const RFC 里也提过 `T: const Destruct`（析构是常量级的）。

## 值得单独说的一点

Arm 本来的动机只是支持可伸缩向量扩展（这对 Rust 也有价值——Rust 的一个优势就是能榨出处理器的全部能力，包括那些独特扩展）。但他们没有把它当成特例塞进 Rust，而是推动了一个**通用**改进，顺带解锁了 extern 类型，以及某种程度上的“保证析构”——后者又能解锁异步 scoped 线程和更好的 Wasm 集成。
