手上这台是 2019 款的 MacBook Pro 16，i9-9880H 加一块 AMD Radeon Pro 5500M（8GB），不是 Apple Silicon。要跑的是 OvisOCR2，ATH-MaaS 出的 0.8B 端到端文档解析模型，喂整页图片直接吐 Markdown，公式是 LaTeX，表格是 HTML，图还会给出位置坐标。

网上的教程基本都假设你有 M 系列芯片，在这台机器上一条都走不通。折腾下来的结果是：PyTorch 那条路被版本链卡死，llama.cpp 官方编译出来的 Metal 后端在独显上直接崩，最后靠 ToshLLM 的一百多个补丁跑起来了，视觉编码 4.8 秒。往上再做了一层通用文档转换，24 页的论文一分多钟转完。

代码在 [ovisocr2-mac](https://github.com/imhun/ovisocr2-mac)，补丁那部分单独拆成了 [llamacpp-metal-amd](https://github.com/imhun/llamacpp-metal-amd)。

## 结论先放这

这几条路都实测过，最终能用一条：

| 方案 | 结果 | 说明 |
| --- | --- | --- |
| PyTorch + MPS | 不可行 | 版本链死锁，本机 torch 上限 2.2.2 |
| llama.cpp Metal（官方） | 输出损坏 | GPU Timeout，输出退化成 `@@@@` |
| llama.cpp Vulkan（MoltenVK） | 输出损坏 | 输出全是 `1`，原因没查到 |
| llama.cpp CPU | 能用但慢 | 单页视觉编码 159 秒 |
| llama.cpp + ToshLLM Metal 补丁 | 能用 | 视觉编码 4.8 秒，输出正确 |

## PyTorch + MPS 为什么在这台机器上不行

一开始的想法很直接：PyTorch 不是支持 MPS 吗，那就用 MPS 跑。结果卡在版本上，而且不是配置问题，是版本链死锁：

```
OvisOCR2 基于 Qwen3.5 架构
  └─ transformers 要 >= 5.0          （只有这样才认识 qwen3_5）
       └─ transformers 5.x 写死要求 torch >= 2.5
            └─ 但 PyTorch 从 2.3.0 起不再发布 macOS x86_64 wheel
                 └─ 本机能装的最高版本停在 2.2.2
```

`uv pip install "torch>=2.5"` 直接告诉你没有匹配的 platform tag：

```
error: No solution found when resolving dependencies
  hint: Wheels are available for `torch` (v2.14.0) on the following platforms:
        manylinux_2_28_aarch64, manylinux_2_28_x86_64, macosx_14_0_arm64, win_amd64
```

2.3 和 2.4 也一样，只有 `macosx_11_0_arm64`。想着能不能绕开版本检查，把 `import_utils` 里的判断放宽，结果立刻撞墙：`ImportError: cannot import name 'DTensor' from 'torch.distributed.tensor'`。数了下 transformers 5.17 里的用量，`DTensor` 出现 85 次，`device_mesh` 73 次，`flex_attention` 53 次，这还没算 `torch.compile` 那 156 处。逐个打补丁显然不现实。

### 顺带发现：这台机器的 MPS 其实是好的

版本链堵死之后本来以为 MPS 在这台机器上根本不能用，毕竟不是 Apple Silicon。顺手写了 `scripts/mps_probe.py` 测了一下，结果有点意外，MPS 不但能跑，还比 CPU 快：

| 测试项 | CPU | MPS | 结果 |
| --- | --- | --- | --- |
| 1024×1024 矩阵乘 ×100 | 0.561 s | 0.435 s | MPS 快 1.29× |
| 迷你 Transformer block (seq=512, d=256) | 4.4 ms | 2.9 ms | MPS 快 1.52× |
| matmul 数值误差 | — | 2.3e-05 | 正常 |
| softmax 数值误差 | — | 7.5e-09 | 正常 |

DeltaNet 那几个关键算子，depthwise `conv1d`、`cumsum`、`einsum`、`triu`、`index_add`，还有手写的 RMSNorm，在 MPS 上全部算对，相对误差 1e-7 量级。唯一的硬件限制是不支持 bfloat16（`TypeError: BFloat16 is not supported on MPS`），而 OvisOCR2 的权重正好是 bf16，所以不管在哪台机器上都得转成 fp16 加载。

也就是说卡住的是 PyTorch 不再给 Intel Mac 发 wheel，不是硬件。

## llama.cpp 官方编译的两条图形后端都挂了

转 llama.cpp 的时候先踩了个前置问题：Homebrew 装的 llama.cpp 在 Intel Mac 上根本没编译 Metal，`--list-devices` 只列出 `BLAS: Accelerate`。原因还是那个，Homebrew 从 2026 年 9 月起不再支持 Intel x86_64 macOS，不再提供 bottle。所以下面这两个后端都是自己编译的。

### Metal

设备识别没问题，速度也确实起来了，视觉编码从 159 秒降到 39 秒，但输出完全是坏的：

```
ggml_metal_synchronize: error: command buffer 0 failed with status 5
error: Caused GPU Timeout Error (00000002:kIOAccelCommandBufferCallbackErrorTimeout)
...
@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@...
```

查下来根因在 issue #15228：Metal 后端用 `newBufferWithBytesNoCopy(... MTLResourceStorageModeShared ...)` 把权重映射成共享内存（`ggml/src/ggml-metal/ggml-metal-device.m:2214`）。这在核显上没问题，在独显上就是灾难，GPU 每算一次都要通过 PCIe 从系统内存搬权重，带宽卡死，最后触发 GPU 超时。这个 issue 被官方关成了 not planned，也就是说官方不打算修。

### Vulkan

装齐 molten-vk、vulkan-loader、shaderc、glslang 之后，设备也能识别，但输出全是 `1`。日志里有算子回退的告警：

```
warmup: WARNING: the CLIP graph uses unsupported operators by the backend
warmup:          the performance will be suboptimal
warmup: list of unsupported ops (backend=Vulkan0):
warmup:   SOFT_MAX: type = f32, ne = [8580 8580 12 1]
```

一开始把这条告警当成了失败原因，后来发现不对。同一个模型在打上补丁的 Metal 后端上跑得完全正确，日志里的告警列表一模一样，同样的 SOFT_MAX、CONT、PERMUTE、ROPE，只有尺寸随分辨率变。这句话的意思只是那些算子回退到 CPU 跑，性能打折，不是出错。所以 Vulkan 输出全 `1` 的根因也没查到，只能确认症状和 issue #20104 对得上，那个 issue 被标成了 #20029 的重复项。运行前需要指定 ICD：

```bash
export VK_ICD_FILENAMES=/usr/local/etc/vulkan/icd.d/MoltenVK_icd.json
```

## ToshLLM 的补丁把它救回来了

[ToshLLM](https://github.com/engeldlgado/toshllm) 有一整套针对 llama.cpp 的 Metal 后端补丁。做法说起来简单，把它 pin 的那个 commit 拉下来，119 个补丁按文件名顺序打上去，重新编译。补丁是针对特定 commit 验证过的，换版本要重新适配。

启动日志里这两行是补丁生效的标志，官方构建里没有：

```
ggml_metal: device 0: AMD Radeon Pro 5500M (peer group 0, not bridged)
            probed SIMD-group width = 32 (32 = Apple/AMD RDNA, 64 = AMD GCN/Vega)
```

`not bridged` 说明它认出来这是一张独显，`SIMD-group width = 32` 说明它按 RDNA 的组宽调度，没套用 Apple GPU 的默认值。这两点正好是官方构建缺的。

同一条命令、同一张 1240×1754 的页面：

| 后端 | 视觉编码 | 输出 |
| --- | --- | --- |
| Metal（官方） | 39.4 s | `@@@@` + GPU Timeout |
| Vulkan（官方） | ~27 s | 全为 `1` |
| CPU | 159 s | 正确 |
| ToshLLM Metal | 4.8 s | 正确 |

连续跑 3 次都是 12 秒左右，0 乱码。

补丁体系的体量也不小，119 个文件里光 0001 和 0002 两个就 15788 行，等于把整个 Metal 后端重写了一遍，所以换 commit 不是随手能升的。

### 这部分拆成了独立仓库

补丁和 OvisOCR2 其实没什么关系。119 个补丁逐个 grep 过，没有一处提到 Ovis，改的全是 llama.cpp 自己的 Metal 后端、ToshLLM 的动态 MoE 和配套调度。所以拆成了独立的 [llamacpp-metal-amd](https://github.com/imhun/llamacpp-metal-amd)：

```bash
git clone --recurse-submodules https://github.com/imhun/llamacpp-metal-amd.git
cd llamacpp-metal-amd
./scripts/build.sh      # clone、切 commit、打补丁、编译、自检
./scripts/verify.sh     # 单独自检，不用模型
./scripts/install.sh    # 装到全局，多个项目共用
```

OCR 仓库通过 submodule 引用它，自己的构建脚本直接调，产物还是落在 `tmp/llama.cpp/build-metal/`。那边如果已经装到全局，这边就不再重复编译一遍。

补丁是用 submodule 引的，没有复制一份过来。两个好处，一是不用在自己的仓库里再分发一遍 GPL-3.0 的代码，仓库本身能保持 MIT；二是 submodule 天然指向确定的 commit，不会出现「手里这份补丁是哪个版本」的问题。代价是克隆得带 `--recurse-submodules`，所以构建脚本发现补丁目录是空的时候会自己补拉。

自检不用加载模型，这点挺省事。补丁版启动时会打印 `probed SIMD-group width`，官方构建的二进制里连这个字符串都没有，`grep -a` 直接就能验证。所以这一行在不在，就是补丁有没有生效的硬判据，几秒钟出结果。光看「Metal 设备已识别」是不够的，官方版也会识别设备，只是算不对。

装全局的时候命令名用的是 `llama-mtmd-cli-amd`，没敢叫 `llama-mtmd-cli`。那个名字被 brew 装的官方版占着，覆盖它会破坏 brew 自己的记录，而且那版在独显上输出本来就是坏的。编译出来的二进制是自包含的，只依赖系统框架、Metal 库已经内嵌，拷到哪都能跑。安装目录里留了一份 BUILD-INFO，记着 llama.cpp 的 commit、ToshLLM 的 commit 和补丁哈希，回头查「装的到底是哪一版」时用得上。

## 分辨率有个硬上限

跑通之后最麻烦的限制来自 macOS 的 GPU watchdog。分辨率越高，单次 command buffer 的执行时间越长，超过阈值就被系统掐掉，输出直接损坏。实测边界：

| 长边 | 视觉编码 | 结果 |
| --- | --- | --- |
| 1600 | 3.1 s | 正常 |
| 2000 | 7.6 s | 正常 |
| 2400 | 18.2 s | 出现 timeout，这次侥幸正确 |
| 2800+ | 18.4 s | 输出损坏 |
| 3508 | 18.6 s | 输出损坏 |

这个限制绕不过去。`sysctl debug.iogpu.*` 在这台机器上不存在，`nvram boot-args` 是空的，`-ub 128` 把 batch 调小也没用，增加 command buffer 数量同样无效。所以脚本里默认 `--max-side 1600`，超过 2000 的值强制压回 2000，同时对输出做损坏检测，识别 `@@@@` 和重复的 `## 1` 这两种退化形态并告警。

## 单页的二十几秒花在哪

拿 [Tree Borrows](</post/2025-09-13.rust-tree-borrows/>) 论文第 16 页单独测，两张表格，190 DPI 渲染、长边 1600：

| 阶段 | 耗时 |
| --- | --- |
| 视觉编码 | 4.76 s |
| 解码（输出 551 个词） | ~16 s |
| 进程启动 + 模型加载 | ~2 s |
| 端到端 | 27.9 s |

这几项是分开测的，不能直接相加。视觉编码和解码来自直接调 `llama-mtmd-cli` 那次（日志里 `mtmd batch encoding done in 4762 ms`），端到端是脚本那次，含 LANCZOS 缩图和进程开销，加载开销则用一张 320×320 的白图单独估出来，那次总共 2.2 秒、几乎不产生输出，所以基本就是加载时间。

权重一共 700MB（Q4_K_M 505MB 加 mmproj 195MB），被系统缓存之后加载很快。真正拖时间的是解码，表格页输出本来就长。这点在批量场景里很关键：`llama-mtmd-cli` 每次调用都是一个新进程，模型要重载一遍，所以单页成本和页面复杂度、输出长度都强相关。

## 常驻服务：把每页重复付的 2 秒省掉

上面那张表里「进程启动 + 模型加载」那一行，在批量场景里是纯浪费。`llama-mtmd-cli` 是一次性程序，每个进程都要重新 mmap 权重、建 Metal 计算图、初始化 mtmd 上下文，然后才开始视觉编码。用一张 320×320 的白图配 `-n 2` 空转一次，整个进程要 7.6 秒：加载约 2.1 秒，视觉编码约 3.6 秒。前一份每次都重付，24 页全量就是 2.1 × 23 ≈ 48 秒。

`llama-server` 把加载、Metal pipeline 编译、上下文初始化全留在进程里，HTTP 请求只付视觉编码与解码。这个 fork 的 server 支持 `--mmproj`，走 OpenAI 那套 `/v1/chat/completions` 就行。

实测（同一台机器，Tree Borrows 那 24 页）：

| 场景 | 耗时 |
| --- | --- |
| 4 页，每页起一个进程 | 98.6 s |
| 4 页，常驻服务 | 87.9 s |
| 2 页，冷启动（自己起服务） | 36.5 s |
| 2 页，复用已在跑的服务 | 25.3 s |

单页平均省 2.3 秒，页数越多越明显。默认端口 8181，被占用就顺延；端口上已经有同模型的实例就直接复用，省掉连第一次的启动开销。

```bash
# 默认就是常驻模式
python src/pdf2md.py paper.pdf -o out/

# 连到一个已经在跑的实例
llama-server -m models/OvisOCR2-Q4_K_M.gguf --mmproj models/mmproj-F16.gguf \
    -c 16384 -ngl 99 --host 127.0.0.1 --port 8181 -np 1 &
python src/pdf2md.py paper.pdf -o out/ --server-url http://127.0.0.1:8181

# 退回每页起进程
python src/pdf2md.py paper.pdf -o out/ --no-server
```

复用不是无条件的。`-c` 是启动参数，复用别人的实例时自己的 `-c` 不生效，页图 token 多一点就可能被截断，所以复用时会校验模型路径、`modalities.vision` 和 `n_ctx`，对不上就自己另起一个。另外调用方点名了 `-dev` 或 `--no-mmproj-offload` 时一律不复用——那两个也是启动参数，别人的实例大概率没带，Vulkan 上不带 `--no-mmproj-offload` 视觉编码会算错。固定 `-np 1`，slot 数会改变 batch 形状，没有理由再多引入一个变量。

### 输出不一定和 CLI 逐字节相同

这点得说清楚。prompt 拼装是逐块一致的：同样的 `add_text` 序列、同样的 35×50 图像网格、同样 122 个文本 token。但送进模型的 decode 调度不一样——CLI 把媒体块和文本块合成一次 `llama_decode`，服务端分成两次，浮点累加顺序不同，贪心解码在接近的 logit 上就可能翻牌。

实测后果：`pdf2md.py` 用到的部分（`<table>` 和 `<img>` bbox）**完全一致**，论文那几页的 Markdown 逐字节相同，裁图和锚点匹配都没变。但自由格式的 Markdown **不保证**，两张合成测试页上出现过段落被拆开、`\qquad` 处的公式被拆成两个 `$$` 块、`border="1"` 变成 `border=1`。内容都在，只是分段不同。要严格复现 CLI 的输出就加 `--no-server`。

这个结论容易被说过头。论文那几页恰好一致，不等于普遍成立——测试页上就分叉了。判断依据得是「prompt 拼装是否逐块一致」加上「下游只取结构化的表格和坐标」，而不是「跑几页看着一样」。

### 一个顺序上的坑

走 `/v1/chat/completions` 时，content 里的 image 块**必须排在 text 块前面**。CLI 是把媒体标记拼在 prompt 最前面的（`mtmd-cli.cpp` 里 `mtmd_default_marker() + params.prompt`），服务端按 content 数组的顺序展开。顺序反了 prompt 就真的不一样了，同一页会被拆段、`\qquad` 处的公式会被拆成两个 `$$` 块。这个不明显，因为两条路径都能正常返回结果，只是内容有出入。

### 编译

`llama-server` 和 `llama-mtmd-cli` 由同一个 build 产出，但 llamacpp-metal-amd 的 `scripts/build.sh` 只编了后者一个 target，所以在 `scripts/build.sh` 里补了一步，在同一个 build 目录里 `cmake --build -t llama-server`。补丁在 ggml 层，对 server 同样生效，不用重新适配。补编失败不致命——找不到 `llama-server` 就自动退回逐页起进程的旧路径。

## 整份文档转 Markdown

能跑起来只是第一步。真要处理整份文档，不能一张一张图喂给 OCR：正文交给它太慢，交给文本提取又丢表格和图。所以让两个工具各干自己擅长的部分。

anydoc 是 Rust 写的，读 PDF 的文本层和字体元数据，正文、斜体、超链接都很完整，速度是毫秒级，缺点是把表格压成平铺文本、图片直接丢掉。OvisOCR2 反过来，能还原 HTML 表格、能报出图表位置，代价是每页几十秒。

于是流程是：anydoc 转全文，pymupdf 挑出含图表的页，只对这几页跑 OvisOCR2，最后按文本锚点把补充内容插回正文。

```bash
python src/pdf2md.py paper.pdf -o out/
python src/pdf2md.py paper.pdf -o out/ --pages 6,12     # 手动指定页
python src/pdf2md.py scan.pdf  -o out/ --no-anydoc      # 扫描件，正文也交给 OCR
```

### 挑页的信号

判断哪页有图表，只对命中的页跑 OCR，所以判据既要抓得住真图真表，又不能把无关页面排进队列——OCR 一页二三十秒，误判的代价是实打实的时间。

一开始的规则很粗：

```python
n_img = len(page.get_images(full=True))      # 位图对象
n_tab = len(page.find_tables().tables)       # pymupdf 判定的表格
n_draw = len(page.get_drawings())            # 矢量绘图数量 >= 15
```

在 5224 页的语料上（各种中文报告、白皮书、发票、合同、论文），这套规则命中 **89.1%** 的页，等于没筛。三条信号各自有各自的假阳性：

| 信号 | 假阳性长什么样 |
| --- | --- |
| 位图 | 每页右上角一枚 logo、页脚一枚印章 |
| 表格 | 代码清单里带框的标签列表被当成 3×2 的表 |
| 矢量 | 4×4 的箭头头部、页眉细线都算一条路径 |

那个最典型的假阳性就是这张表的产物。pymupdf 把代码示例里的 `root: Unique`、`tmp, ptr: Reserved` 这几个带框标签看成了 3 行 2 列的表，但每一行只有一列有内容，填充率 50%；同时这页的矢量路径有 30 条，正好过 15 那条线。两个弱信号叠在一起，就被捞进来了。OCR 跑完发现既没有表格也没有图，白花二十几秒。

现在三条都加了形状约束：

- **位图**：面积至少占页面 0.5%。只看面积不看数量，一枚 logo 不该让整页进队列。
- **表格**：`rows >= 3`、`cells >= 6`，且平均每行至少 1.5 个非空格。真表至少两列有内容。这里按「非空格 / 行数」卡而不是按行列数卡，是为了不误杀稀疏的真表——有一份社保缴费明细 420 个格子、填充率只有 53%，照样该命中。
- **矢量**：取矢量墨迹的**包围盒**（不是面积累加），要同时占页面 15% 以上、且高度达到 150pt。铺满 60% 以上的单个矩形当背景排除掉。

包围盒而不是累加面积，是因为两种图形形状完全相反：状态机这类图是几十条互不相连的小笔画，单条面积不大，但整体摊在一大片区域上，包围盒很大；而代码块的灰底板是几个大矩形，累加面积会爆表，包围盒反而收得住。高度条件是第二道保险——图是成块的，代码清单是横条，只看面积的话代码块也凑得够。

同语料下命中率从 89.1% 降到 28.5%。掉的那些基本都是该掉的：

| 文档 | 旧 | 新 | 说明 |
| --- | --- | --- | --- |
| `expense-servicek.pdf` | 3033 | 3 | 3033 页报销单，每页一枚 logo |
| `JuiceFS 产品白皮书.pdf` | 35 | 12 | 右上角 logo 在每一页上 |
| `tree-borrows.pdf` | 4 | 3 | 那个代码示例页，OCR 出来啥也没有 |
| `unsound-oopsla16.pdf` | 1 | 0 | 15 条发丝线 |

三个阈值都留了命令行开关（`--min-image-area`、`--fig-area`、`--fig-height`），每页的命中理由也会打出来，方便判断要不要调：

```
[ovisocr2] 命中原因: p6=figure  p12=figure  p16=table
[ovisocr2] OCR 目标页: [6, 12, 16]  3/24
```

**已知的漏检**也得记一笔：靠「有填充的矢量图形」画出来的图会被漏掉。墨迹面积不到 15% 的信息图就抓不到——OpenHarmony 2022 年报第 31 页那张信息图，矢量墨迹只占页面 9.5%、28 个 item，判不出来；同样内容的整页位图反而没问题，因为走的是位图那条信号。遇到了就调小 `--fig-area`。

这个启发式试过好几个候选特征才定下来，中途有几个走不通的记一下，省得以后再试一遍：按路径**条数**分不开（真图那两页是 37 和 35 条，假阳性那页 30 条）；按**曲线**数量分不开（有页的贝塞尔曲线项比真图还多）；**聚类**连通分量没用，状态机的笔画本来就是散开的，最大连通块只占页面 1%；**文本密度**方向是反的，真图那页的文字填充率 0.45，比代码块那页的 0.18 还高。

### 插回正文时的坐标错位

anydoc 的输出是纯文本流，OCR 的结果要插回对应页的位置。做法是取该页最有辨识度的一段文字（80 字符以上、去掉行号前缀）当锚点，在归一化后的正文里模糊匹配，相似度超过 0.6 就插在匹配位置之前。

这里踩了个不容易发现的坑。归一化函数把连续空白折叠成一个空格，而插入函数一开始只数非空白字符：

```python
def norm(s):
    return re.sub(r"\s+", " ", s).strip()
```

两边坐标系对不上，位置会不断前移，最后插进单词中间，`tracking` 被切成 `t` 和 `racking`。这个 bug 不报错也不抛异常，只会悄悄把文档切坏，跑通一遍完全看不出来。修法是让插入函数也把空白当作占位字符来数。

### Office 格式走另一条路

docx、pptx、xlsx 这类格式不需要渲染，也不需要 OCR。anydoc 的 `to_document()` 能直接给出结构化对象，表格的合并单元格、图片的原始字节都在里面，导出比 PDF 那条路干净得多：

- 表格网格用 `origin` / `covered` 表示，合并单元格靠 `cell.row_span` / `col_span`，能还原成带 `colspan` 的 HTML 表格
- 单元格内容在 `slot.cell.blocks[].content[].text`，比正文多一层 `.cell`
- 列表项在 `block.list.items[].blocks`，不在 `content` 里
- 图片在 `content[].source.asset_id`，对应 `doc.assets[]` 的 `.data`，导出是原始字节，无损

两个 API 上的坑记一下：`to_document()` 不接受 PDF，会报 `UnsupportedError: PDF converts directly to Markdown`；而 `to_markdown()` 处理 docx 时标题、列表、表格都对，但图片会完全消失，连占位符都不留。

### 实测结果

24 页的 Tree Borrows 论文：

```
[ovisocr2] 命中原因: p6=figure  p12=figure  p16=table
[ovisocr2] OCR 目标页: [6, 12, 16]  3/24
[ovisocr2] llama-server 就绪，耗时 2.1s
[ovisocr2]   补入 2 图 / 0 表格      ← p6 状态机
[ovisocr2]   补入 1 图 / 0 表格      ← p12 状态机
[ovisocr2]   补入 0 图 / 2 表格      ← p16
[ovisocr2] p6 插入正文（匹配 0.95）
[ovisocr2] p12 插入正文（匹配 1.00）
[ovisocr2] p16 插入正文（匹配 1.00）
```

总共 1 分 20 秒上下（多次测量在 75 到 81 秒之间浮动），产出 92468 字符的 Markdown 和 3 张裁好的图。24 页全部跑 OCR 要 8 分钟以上，只挑 3 页省掉了九成时间。

和之前那版对比：命中从 4 页降到 3 页（那个代码示例页被筛掉），耗时从 98.6 秒降到 81 秒左右，产出字符数和裁图数量都没变。严格对照同一批 4 页的话，98.6 秒降到 87.9 秒，那 10.7 秒是常驻服务单独贡献的；再把假阳性那一页整个去掉又省下二十几秒。两项加起来理论上是二十一秒出头，实测十八秒，差在测量波动上——单页 OCR 的耗时本身受页图复杂度和输出长度影响挺大，同一页重复跑能差几秒，所以别把这种加法当精确账。

Office 那条路快得多，同一个测试 docx：

```
[ovisocr2] anydoc 结构化导出: 14 ms, 265 字符, 1 张图（无损，无需 OCR）
```

整条命令 0.26 秒结束。

## 复现

克隆后一条命令装完：

```bash
./scripts/build.sh
```

脚本依次做环境检查、装 Python 依赖、下 GGUF 权重、构建 llama.cpp（这一步调 [llamacpp-metal-amd](https://github.com/imhun/llamacpp-metal-amd) 完成 clone、打补丁、编译、自检）、补编 `llama-server`、跑冒烟测试。每步都先检查是否已完成，重复执行会直接跳过，首次编译 5 到 15 分钟。国内下权重可以带上镜像：

```bash
HF_BASE=https://hf-mirror.com/Abiray/OvisOCR2-GGUF/resolve/main ./scripts/build.sh
```

冒烟测试会画一张带表格线的小图跑一次真实 OCR，检查输出非空、没有 `@@@@` 这类退化内容、日志里能读到 Metal 设备，这三项过了才说明补丁和 GPU 后端真的在工作。

构建脚本这块还踩了个自己给自己挖的坑，值得记一下。最早 `tmp/llama.cpp` 是官方构建留下的目录，里面躺着一个没打补丁的 `build-metal/bin/llama-mtmd-cli`。脚本当时只判断「二进制存在就跳过编译」，于是补丁打上了、编译跳过了、自检去查那个没打补丁的二进制，报「没有检测到 Metal 设备」。查了半天才发现是脚本的锅，不是补丁的问题。现在补丁标记会写进构建目录，对不上就把旧目录移开重编。

仓库结构：

| 路径 | 说明 |
| --- | --- |
| `src/ovisocr2_llama.py` | 单页/批量 OCR，自动挑二进制，含缩图与损坏检测 |
| `src/pdf2md.py` | 通用文档转 MD，PDF 走混合流程，Office 走结构化通道 |
| `src/ocr_server.py` | 常驻 llama-server 的 HTTP 客户端：起、复用、关 |
| `src/ovisocr2_pytorch.py` | PyTorch / MPS 版本，给 Apple Silicon 用 |
| `third_party/llamacpp-metal-amd` | submodule，llama.cpp 的 Metal 补丁构建 |
| `scripts/build.sh` | 一键构建，顺带补编 llama-server |
| `scripts/mps_probe.py` | MPS 能力与性能探测 |
| `scripts/fetch_gguf.sh` | GGUF 下载脚本，`HF_BASE` 可指向 hf-mirror |
| `requirements.txt` | llama.cpp 路径的运行依赖（pillow / pymupdf / firecrawl-anydoc） |
| `requirements-torch.txt` | PyTorch 路径的依赖，需 Apple Silicon |
| `tmp/llama.cpp/` | 打过补丁的 llama.cpp 和 `build-metal/`（不入库） |
| `models/` | GGUF 权重，共 700MB（不入库） |

常用命令：

```bash
python src/ovisocr2_llama.py page.jpg -o out                 # 单页，默认 1600
python src/ovisocr2_llama.py scans/ -o out --max-side 2000   # 更清晰，更慢
python src/ovisocr2_llama.py page.jpg -o out -v              # 透传 llama.cpp 日志
python src/ovisocr2_llama.py scans/ -o out --no-server      # 退回每页起进程
python src/pdf2md.py paper.pdf -o out/                       # 完整文档，常驻模式
python src/pdf2md.py paper.pdf -o out/ --fig-area 0.08      # 放宽矢量判据
```

`ovisocr2_llama.py` 找二进制的顺序是 `tmp/llama.cpp/build-metal/bin/llama-mtmd-cli` → 全局安装 → `PATH` → 官方构建。加 `-v` 会把 llama.cpp 的原始日志打出来，排查输出异常时能直接看到接管的是不是 Metal 后端、视觉编码花了多久。

## 还没解决的问题

- 分辨率天花板锁在 2000，小字密的文档（扫描合同、竖排古籍）可能不够用，目前没找到绕过 watchdog 的办法
- ToshLLM 的补丁绑定特定 commit，想跟进上游得重新适配一万多行补丁
- GGUF 量化版本不全，`OvisOCR2-Q8_0.gguf` 在镜像上下载不完整，只到 1.9MB，目前只用 Q4_K_M
- 选页判据里，靠填充矢量图形画的图还会漏（墨迹不到 15% 就抓不到）。整页位图的没问题，纯矢量信息图要靠 `--fig-area` 往下调
- 常驻服务和 `llama-mtmd-cli` 的自由格式输出不保证逐字节相同，原因查到是 decode 调度不同导致的浮点差异，没找到让它对齐的办法
