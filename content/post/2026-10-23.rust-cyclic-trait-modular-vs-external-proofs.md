Rust 要支持循环 trait impl，只能用**模块化证明**——supertrait 义务由 impl 自己承担。作者原先倾向的**外部证明**（由使用 impl 的代码承担）和 unsafe trait 的既有语义直接矛盾，走不通。更进一步，作者认为 unsafe 附加的条件本质上就是同一类义务的一般形式，所以模块化证明不是可选项，是唯一解。

<!-- more -->

## 问题：supertrait 由谁证明

supertrait 是一条编译器必须兑现的蕴含：

```rust
trait Magic: Copy { }        // X: Magic ⇒ X: Copy

fn is_magic<T: Magic>() {
    is_copy::<T>();           // 合法，靠的就是这条蕴含
}
```

于是设计分水岭落在一个问题上：**谁负责证明 supertrait 义务成立**。

## 两套方案对比

| | 模块化 | 外部 |
|---|---|---|
| 谁证明 supertrait | impl 自己 | 使用 impl 的代码 |
| `impl Magic for String` | 非法 | 合法，但不可用 |
| `is_magic::<String>()` | 编译通过 | 编译不过 |
| 函数类比 | 调用方信任签名 | 调用方要核对函数体和返回类型 |
| 作者结论 | ✅ 唯一选项 | ❌ 与 unsafe 不兼容 |

外部证明的推理规则是：impl 只提供浅层证据，深层证据（含 supertrait）由调用方凑齐——

```
Shallow(String: Magic)
Shallow(String: Copy)
---------------------------- Magic fully implemented
String: Magic
```

所以 `impl Magic for String` 合法，但因为凑不出 `Shallow(String: Copy)`，它始终推不出 `String: Magic`，写了也用不了。

## 模块化证明必须补一条规则：禁止自证

不设限的话，证明会绕回起点：`String: Copy` ← `Magic` 蕴含 `Copy` ← `String: Magic` ← `impl Magic for String` 存在，于是错判 impl 合法。

**规定：证明某个 impl 合法时，该证明不能递归依赖这个 impl 本身。** 防自证的具体机制作者另文再谈。

soundness 不受影响：impl 非法则整个程序过不了类型检查，其他代码对契约的假设落空也不会出事。

## 外部证明为什么被否决

`unsafe impl` 由 impl 自证条件、其他代码无条件信任，这是 Rust 现有语义：

```rust
unsafe trait NullWord { }   // 可安全从 0_usize transmute 过来的类型

fn foo<T: NullWord>() -> T {
   std::mem::transmute(0_usize)   // 靠 T: NullWord 才安全
}

// 无效 impl：断言 Box 可以是 null
unsafe impl<T> Nullable for Box<T> { }
```

无效 impl 一存在，`foo::<Box<u32>>()` 就是 UB，责任明明白白在 impl。矛盾在这里：外部证明说 impl 不足以证明 supertrait 成立，却要求它单独证明 unsafe 条件有效——**同一个 impl，一边不被信任，一边又被信任**。
