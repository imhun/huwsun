> 来源：[Battery packs: Let's talk about crates, baby](https://smallcultfollowing.com/babysteps/blog/2026/07/15/battery-packs/)，Niko Matsakis，2026-07-15

问题很具体：crates.io 上的库又多又好，但**挑起来太费劲**——这是 Rust 新手最常抱怨的一点。battery pack 的做法是给一组默认答案，同时不锁死你：它本质上只是一份推荐清单，随时可以换掉。

<!-- more -->

## 是什么

一个叫 `X-battery-pack` 的 crate，它的依赖就是你推荐的那些库。目前有 CLI、后端服务、嵌入式（基于 Embedded 工作组的 [Awesome Rust 清单](https://github.com/rust-embedded/awesome-embedded-rust)）、错误处理几个包。

```bash
cargo install cargo-bp

cargo bp list      # 列出有哪些 battery pack
cargo bp add cli   # 把一套 CLI 常用的库加进项目
```

`cargo bp add embedded` 是更完整的演示，会进一个交互界面让你挑。想自己做一个：

```bash
cargo bp new battery-pack
```

模板会问你几个问题、把骨架建好，接着用 `cargo add` 把你推荐的库加进去就行。

## 关键设计：谁都能发

这是它和“给 Rust 做个扩展标准库”那类想法的根本区别。

- **能针对特定需求定制。** CLI 和后端服务面向“普通电脑”，而嵌入式工作组完全可以发一个专注 no-std 和体积优化的包
- **绕开“谁来定”这个难题。** 最懂该用哪些库的，是**正在做同类系统的人**。甚至可以更窄，比如专门围绕 [embassy](https://embassy.dev/) 生态

## 能加的未必是依赖

也可以是**配方或模板**。比如 `cargo bp add ci` 能一键配好那些你一直想要、但懒得动手的 GitHub Actions。模板系统目前基于 [minijinja](https://github.com/mitsuhiko/minijinja)，还比较轻，后面会扩展。

## 层级结构

依赖和特性可以分组到**类别**里，每个类别再区分“最多选一个”还是“任选若干”。跑 `cargo bp add embedded` 看到的是：

```text
 ▼ Concurrency Framework (pick at most one)
 > ○ ✦ embassy [embassy-executor, embassy-sync, embassy-time]
   ○ ✦ rtic [cortex-m, rtic]

 ▼ Display & Graphics (pick any number)
   [ ] ✦ display-ssd1306 [embedded-graphics, ssd1306]
   [ ] ✦ display-st7789 [embedded-graphics, st7789]
```

“并发框架”只能选一个，“显示驱动”可以多选——这个区分在选型时很有用。

## 顺带能解决的两件事

| 方向 | 做法 |
|---|---|
| 支持维护者 | 每个官方背书的电池包配一个“生态基金”：公司或个人出钱，换取早期补丁、安全披露等权益，钱用来养这些 crate 的维护者、补功能 |
| 促进互操作 | 工作组坐下来谈推荐时，会自然发现哪些地方标准不统一。网络服务组一上来就发现：大半人在用 [tokio](https://tokio.rs/)，但有些大厂内部用自己的 runtime。现在每个库各自实现一套小 trait 来兼容，而官方电池包能提供一块中立的落脚地 |

作者的期待是：[Rust 商业网络](https://rustfoundation.org/rust-commercial-network/)（RCN）里的工作组联合发布电池包——那反映的是他们真正在用的依赖。

## 风险

最明显的一条：**谁都能发，就可能冒出一大堆电池包**，反而帮不上忙。作者不太担心——他觉得大家会先涌向少数几个明显的选择，熟悉之后反而更有兴趣去挖 crates.io 上的小众包。

更值得警惕的是**生态停滞**。历史上这种事反复出现：某个领域有个占主导的库走“传统路线”，然后有人提出更好的替代方案慢慢取代它。CLI 参数解析就是例子——先是 [docopt](https://crates.io/crates/docopt)，然后 [clap](https://crates.io/crates/clap) 带来更结构化的做法，再后来 structopt 把 clap 接上自动派生，写个数据结构就完事（这套现在已经是 clap 的标准用法）。他不希望电池包挡了“下一个 clap”的路。

三点设计能缓解：

- **它是薄抽象。** 你不“依赖”电池包，你依赖的是里面的 crate。某个包从 docopt 换成 clap，对你的代码毫无影响
- **谁都能发**，所以可以围绕新方案做变体电池包，帮它起步
- **做对了反而是助力。** 新库现在靠口口相传扩散，而如果一个组把新方案写进自己的电池包，就是个明确信号：我们认定这是新的主流做法

## 背后是一条设计公理

“**永远押注生态**”——这既是当初选择小标准库 + 包管理器的原因，也是为什么电池包设计成人人可发。

但植物长到一定高度就需要支架。任何成功的生态到了一定规模，都需要再搭一层结构才能继续长；少了这层，就会出现“一层隐性知识”（[Rust 愿景文档里受访者的说法](https://blog.rust-lang.org/2025/12/19/what-do-people-love-about-rust/#example-the-wealth-of-crates-on-crates-io-are-a-key-enabler-but-can-be-an-obstacle)），变成新人的障碍。作者认为 crates.io 已经到了这个节点。

说到底，如果有更好的办法也无妨——只要能让人**找到**（并且**资助**）需要的 crate 就行。
