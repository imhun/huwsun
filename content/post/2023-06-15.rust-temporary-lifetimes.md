临时值默认在**最内层语句结束**时析构，俗称“下一个分号”。这条规则 2014 年定下，配上一处延长规则和三处例外，构成一个经常咬人的角落。

<!-- more -->

它出的问题分两类：**该析构的时候没析构**（后果通常是死锁），和**不该析构的时候析构了**（后果是编译不过）。改这些规则会改变析构时机，所以只能跨 edition 做。

## 默认规则和三处例外

借用一个“产生值的表达式”（rvalue）就会产生临时值。`&foo()` 最直白，必须先把 `foo()` 的结果落到某处才能取引用。多数时候借用是隐式的：`get_data().is_empty()` 能写，是因为 `get_data()` 的返回值先落进临时值，再 deref 成 `&[T]`。

“最内层语句”这个说法有三处例外：

| 位置 | 实际行为 | 原因 |
|---|---|---|
| 块尾表达式 | 推迟到包围这个块的语句结束 | 尾表达式不算语句 |
| `if` / `while` / if 守卫 | 条件周围自带作用域，进函数体前就析构 | 条件产生布尔值，不可能有引用还活着 |
| 函数体尾表达式 | 函数返回前析构 | 它不被任何语句包含 |

第三条有个容易踩的后果：

```rust
fn last() -> Option<&Datum> {
    get_data().last()   // 编译不过：vector 在返回前就被 drop 了
}
```

另外 `match` 和 `if let` 的 scrutinee **不是**临时作用域，这一点和 `if` 不同，下面会看到它就是死锁的来源。

## 延长：从语句到块

如果能明显看出临时值要存进局部变量，就延长到最内层块。规则纯看语法，不看类型，也不做名字解析。

```rust
let t = &foo();
// 等价于
let tmp;
let t = { tmp = foo(); &tmp };
```

会延长：`&foo()`、`Foo { x: &foo() }`、`(&foo(), )`、`[&foo()]`、`let ref t = foo()`。
不延长：`some_function(&foo())`、`SomeTupleStruct(&foo())`——都长得像函数调用，编译器不猜。

## 问题一：锁活得太久

```rust
match lock.lock().data.clone() {
    //     ------ guard 活到整个 match 结束
    Data { ... } => {
        lock.lock(); // 死锁
    }
}
```

同样的写法在 `if` 上不会出问题，因为条件自带作用域：

```rust
if lock.lock().something {  // 取锁、释放
    lock.lock();            // 可以再次取锁
}
```

换成 `if let` 或 `match` 就死锁。这种不一致还连累了 let-else、if-let 的脱糖——没有统一行为可照。

## 问题二：数据死得太早

```rust
let last_elem = get_data().last();
drop(last_elem); // 错误
```

`last` 要 `&self`，所以返回的 `Vec` 得先落进临时值；而这个临时值在分号处就没了。

RFC 66 想修这里：如果函数签名会从某个实参返回引用（`fn last(&self) -> Option<&T>`），就延长该实参里临时值的生命周期。但即便实现了也有盖不住的：

```rust
let l = get_data().last().unwrap();
drop(l); // 仍然错误：unwrap 的签名 fn(Option<T>) -> T 不含引用
```

还有一处不对称——带标签的 `break` 不享受延长：

```rust
let x = 'a: { break 'a &vec![0]; }; // 错误
let x = { &vec![0] };              // 可以
```

## 想要的行为

第一类是**收紧**，四个对应关系：

1. match 里取的锁在进入分支前释放
2. `if` / `if let` / `match` 对 scrutinee 的处理完全一致
3. `{expr}` 不产生活过块末尾的临时值
4. `{expr}` 和 `'a: { break 'a expr }` 等价

第二类和上面可能冲突，方向相反：`let x = get_data().last();`、`let x = Event(&[1, 2, 3]);` 这类应该能编。

## 怎么取舍

**收紧**最彻底：去掉语法延长，块尾表达式在返回时析构，match scrutinee 在匹配前析构。代价是这些今天能编的写法会编不过——

```rust
let x = &vec![];
let x = Foo { x: &[1, 2, 3] };
match &foo.borrow_mut().parent { Some(ref p) => .. }
{ let x = { &vec![0] }; ... }
```

好处是“match 作为函数尾表达式”那个反直觉的坑顺带修好了。

**放宽**（让编译器猜）能救回 `get_data().last()`，代价是 `let x = locked_vec.lock().last()` 也会把锁延长到块末尾——大概不是使用者想要的。作者说他在真实代码里从没见过 `cell.borrow_mut()` 那类写法被延长坑到，“困惑**总是**出在 match 上”。

**显式延长**是第三种，用 `expr.let`：

```rust
let x = get_data().let.last();
// 等价于
let tmp = get_data();
let x = tmp.last();
```

## 两条约束

判断析构时机**不能依赖借用检查器**——比最早的规则略宽松，以前连名字解析和类型检查的结果都不许看。

规则还应该偏向**短**：实践中的麻烦多来自锁被持有太久；而临时值过早释放通常只是编译错误，属于易用性问题，不是可靠性问题。
