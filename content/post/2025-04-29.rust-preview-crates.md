## 问题

有些特性我们**确定**要给用户，但**不确定**该在语言或标准库里怎么暴露。现有两个工具都不合用：

| 工具 | 为什么不够 |
|---|---|
| nightly | 什么保证都没有，所以大家只拿它写玩具项目。语法类特性（比如 `let-else`）这样够了，但看不到一个特性对生态的影响 |
| edition | 能改语法含义且 opt-in，代价是逼人重学、让书过时。为了一个将来还要改形状的特性付这个代价，太高 |

具体的例子是 const trait。有几种写法在考虑，都是用来表达“一个能在编译期执行、内部会调用 `T::default` 的函数”：

```rust
const fn compute_value<T: ~const Default>()
const fn compute_value<T: const Default>()
const fn compute_value<T: Default>()
```

作者有偏好，但把握只有八九成。而且真要定下来，还得看 async 那边怎么走，以及 `const fn` 实际用起来哪种模式常见——这种事事先很难估准。

## 方案

发一个 rust-lang 组织名下的特殊 crate：和标准库一样能访问编译器内部，但在 stable 上可用。它只暴露一个宏：

```rust
const_preview::const_item! {
    const fn compute_value<T: ~const Default>() {
        // 内部用编译器内部 API 解析内容并施加特殊语义
    }
}
```

想改语法（比如把 `~const` 换成 `const`）就发 v2.0，同时用 [semver trick](https://github.com/dtolnay/semver-trick) 把 1.0 重写成转发，老代码继续能用。等对这个宏满意了，就并进语言本身，preview crate 退化成“脱糖成真正的语法”。

顺带的好处是别人能做实验：想试“`T: Default` 默认就是 const”，写个 wrapper 脱糖到 `const_preview::const_item` 就行。

## 已知的坑

**和编译器版本对不上怎么办。** libstd 能和编译器一起发布，所以可以用那些不稳定、每个版本都可能变的内部 API；crates.io 上的 crate 做不到。办法是：预览功能实际由 **sysroot 里随编译器一起发布的 crate** 提供，它们除了我们“钦定”的那个 crates.io crate 之外不能直接用——基本上就是一层 shim。为什么不直接让人用 sysroot 那个 crate？因为不够显眼，而且没法在 crates.io 上追踪反向依赖来评估使用情况。

**宏太重。** 作者也考虑过 `p#` 关键字（preview）：

```rust
#[allow(preview_feature)]
p#const fn compute_value<T: p#const Default>() {}
```

这种方式侵入性小，但 crate 方案允许我们把 `p#const` 发到 v2.0，所以更好。

**decorator 体验更好，但不行。** `#p[const_preview::const_item]` 在 rust-analyzer 里体验更好，但 decorator 只能加在合法 Rust 语法上，那就意味着解析器要永久支持 `~const` 这类东西，而作者更希望把这份复杂度隔离在 `const_preview` 里。

**风险是它被用滥。** 如果 preview crate 变成“体验有缺口也照稳定”的常用手段，就会堆出一大堆永远不会被挪进 Rust 本体的 preview crate。

## 这不是新思路

Ember 把“底层先行”这条路制度化了：他们的 edition 不是按时间点，而是范式迁移。通往 edition 的过程中，先把核心 API 发出来，社区在上面写封装、试探各种用法，等最佳实践固化了再宣布 edition 就绪。Java 有 preview feature，但没有 semver 保证它会留下来。

## 现状

还在“早期构思”阶段，没定。但作者一直认为发布流程需要一个**中间态**——这个想法在 [Stability without stressing the !@#! out](https://smallcultfollowing.com/babysteps/blog/2023/09/18/stability-without-stressing-the-out/) 里也提过，preview crate 大概是工具箱里值得备上的一件。

至于“为什么不干脆现在就定下来”：他确实觉得团队有时太谨慎，但“赶紧让东西出去”和“花时间评估泛化方向”之间的张力到底是问题固有的，还是工作方式带来的，他也说不好。
