Polonius 用的那种“子类型关系的结果就是一组 subset 关系”的模型，碰到 higher-ranked 类型就不够了。

<!-- more -->

## 从逆变说起

fn 类型在参数上是**逆变**的，所以

```text
fn(&'a u32) <: fn(&'b u32)
```

成立的代价是 `'b: 'a`——能用 `'a` 引用调用的函数，才能当作能用 `'b` 引用调用的函数（只要 `'b` 能当 `'a` 用）。这里 `'b` 是一个**具体**的 region，所以两边能建立子集关系。

换成 higher-ranked：

```text
fn(&'a u32) <: for<'b> fn(&'b u32)
//             ^^^^^^^ 超类型要求参数可以是*任意*生命周期的引用
```

这里不存在一个具体的 `'b` 可以拿来建关系。它对应的约束是 `forall<'b> { 'b: 'a }`——`'a` 必须包含**所有**可能的借出。这不可能，所以应该报错。

反过来：

```text
for<'b> fn(&'b u32) <: fn(&'a u32)
```

得到 `exists<'b> { 'a: 'b }`——子类型一侧的 `for` 绑定实例化成“存在”。`'b` 取 `'a` 本身就行，可解。

## 约束语言

所以要表达 higher-ranked 子类型（以及 trait 匹配）的结果，得把基础谓词加上量词：

```text
Constraint = Subset
           | Constraint, Constraint   // 且
           | forall<R1> { Constraint }
           | exists<R1> { Constraint }
Subset = R1: R2
```

## 怎么归约回简单的 subset

关键观察：这些约束最终只需要归约成 Polonius 能处理的 subset 关系。看这个例子（加了返回类型和第三个 region `'c'`）：

```text
for<'b> fn(&'b u32) -> &'b u32
           <:
        fn(&'a u32) -> &'c u32
```

给出

```text
exists<'b> { 'a: 'b, 'b: 'c }
```

它可解，但只在 `'a: 'c` 时成立。所以整个“丰富约束”可以归约成一条简单的 `'a: 'c`。

归约时要区分 **bound region**（被 `forall` / `exists` 绑定的，比如 `'b`）和 **free region**（不受绑定的）。归约只关心两件事：

**一、有没有不可满足的部分？** 通常出现在某个 `forall` 绑定的 region 出现在右边时。

| 约束 | 结果 |
|---|---|
| `forall<'b> { 'b: 'a }` | 不可满足 |
| `forall<'x, 'y> { 'x: 'y }` | 不可满足 |

**二、对 free region 有什么影响？** 有时 bound region 只是“中间人”，在 free region 之间传递子集关系。

| 约束 | 归约结果 |
|---|---|
| `exists<'b> { 'a: 'b, 'b: 'c }` | `'a: 'c` |
| `forall<'b> { 'a: 'b }` | 可满足，但仅当 `'a: 'static` |

最后一条值得解释：`'static: R` 对任何 region `R` 都恒真，这就是为什么 `'a: 'b` 对所有 `'b` 都成立是可能的。用 Polonius 的话说，`'static` 代表**空集**的借出——空集当然是任何集合的子集。

## 这就是 Hereditary Harrop 谓词

上面做的事，本质是取一个基础谓词（`R1: R2`），再“加进” `forall` / `exists` 这些形式。这正是 [Chalk 那篇](https://smallcultfollowing.com/babysteps/blog/2017/01/26/lowering-rust-traits-to-logic/#type-checking-generic-functions-beyond-horn-clauses)里讲的 Hereditary Harrop（HH）谓词：它是一套可以套在**任意**基础谓词集合上的通用结构，完整版本还包括“或”和“蕴含”。

```text
Constraint = Subset
           | Constraint, Constraint   // 且
           | Constraint; Constraint   // 或
           | forall<R1> { Constraint }
           | exists<R1> { Constraint }
           | if (Assumption) { Constraint }
```

rustc 今天不用这么丰富的东西，但作者认为最终会需要。HH 的好处是可以用基本的 Prolog 式搜索找出并枚举所有解。

## 这个分层为什么好

**Polonius 完全不用关心这些丰富约束。** 子类型和 trait 匹配算法负责产出 HH 约束，把它归约成简单的 subset 约束，再交给 Polonius 做最终推理。每一步都可能单独产出错误。

没解决的部分是**归约算法本身**——这篇只给了例子。作者说他做过一些实验，也想知道是不是有人已经解决过这个问题（他有很强的“在重新造轮子”的感觉）。
